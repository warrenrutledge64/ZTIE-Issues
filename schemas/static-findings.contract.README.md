# `static-findings.contract.v1` + `static-scan-summary.contract.v1` — the static lane (Story 2.1)

> **Status: implemented (Story 2.1).** The static-analysis lane runs four
> non-executing scanners over an artifact routed to `static_analysis`, normalizes
> their output into ONE findings shape, and crosses only a bounded summary to the
> Hub. This is the first Phase-2 lane and one of the two evidence streams Nova Pro
> correlates in Phase 3.

## Two documents, two homes (RD-009 / RD-012)

The static lane produces **two** derived artifacts with **deliberately different
homes**, because one may echo artifact content and one must not:

| Document | Schema | Home | Crosses to Hub? |
|----------|--------|------|-----------------|
| **Normalized findings** (the full evidence) | `static-findings.contract.v1.json` | **Forensic S3** (`findings/<intake_id>/static-findings.json`) | **No** |
| **Scan summary** (bounded, derived) | `static-scan-summary.contract.v1.json` | crosses the RD-013 gate → **Hub** tracking record | **Yes** (fifth envelope kind) |

The full findings document carries rule messages, matched lines, and resource
names — content **derived from** the (untrusted) artifact. Per **RD-009** the Hub
is a control plane that never receives artifact-derived content beyond bounded,
sanitized summaries, so the full document **stays in Forensic**. Only the summary —
per-tool run status, finding counts by severity, the total, the worst severity, the
non-executing flag, and a **pointer** (`findings_s3_bucket` / `findings_s3_key`)
back to the full document — crosses the boundary. The summary schema has **no field**
for finding text, so none can be smuggled across.

## One shape across four tools

Every tool's native output is normalized into the same `finding` object:

- `tool` — which of `cfn-lint` / `cfn-guard` / `checkov` / `bandit`.
- `rule_id` — the tool's **native** rule id verbatim (e.g. `E3012`, `CKV_AWS_20`,
  `B602`, a cfn-guard rule name), so a finding is traceable to the tool's catalog.
- `severity` — the tool's native severity mapped onto ZTIE's normalized ladder
  (`info` < `low` < `medium` < `high` < `critical`). A normalized **evidence**
  severity, not a verdict.
- `check_family` — `iac_lint` / `policy_as_code` / `iac_misconfig` / `sast`, so
  Phase 3 groups the kinds of evidence without re-deriving them from the tool name.
- `message` — bounded human-readable description (inert triage text).
- `location` — `file` + 1-based `start_line`/`end_line` + logical `resource`, when
  the tool reports them.

Phase 3 therefore consumes **one** format regardless of which tool fired.

## Which tools run for which class

The routing decision (Story 1.3) sends both `iac_template` and `raw_script` to the
`static_analysis` lane. The lane picks the appropriate tools per class:

- **`iac_template`** → `cfn-lint` (lint), `cfn-guard` (policy-as-code), `checkov`
  (IaC misconfiguration).
- **`raw_script`** → `bandit` (Python SAST), `checkov` (config/secret scanning over
  the file).

`other_unknown` never reaches the lane (it is safe-rejected in Phase 1).

## Non-negotiables baked into the contracts

- **NON-EXECUTING (RD-001).** Both documents record `non_executing: true`. The
  static lane parses/inspects the artifact; it **never runs it**. Execution is the
  dynamic detonation lane (Story 2.3) on the isolated EC2 host — a separate contract
  (`findings.contract.v1` draft, RD-017).
- **EVIDENCE, NEVER A VERDICT (zero-trust).** Neither schema has a
  `verdict`/`safe`/`approved`/`forward`/`pass_fail` field. `highest_severity` is a
  descriptive roll-up of evidence, **not** a decision. The verdict is Hub-side and
  human-gated (Phase 4).
- **Bounded + allow-list.** `additionalProperties: false` at every level; findings
  and strings are length-capped so a hostile artifact cannot produce an unbounded
  document. When findings exceed the cap the stored document is truncated
  (`truncated: true`) but the per-tool + summary **counts remain the true
  pre-truncation totals**.
- **Integrity-keyed.** Both are bound to `intake_id` + `sha256`; the Hub attaches
  the summary only to the exact artifact it was computed over.
- **Resilient.** A scanner error is recorded (`tools[].status = "error"` +
  `error_reason`) and the lane keeps running the other tools — it does not crash
  (DoD: "does not crash on a scanner error").

## Regenerating the schemas

Both schemas carry a remote `$schema` URL (which `fs_write` refuses), so they are
generated by `python json.dump`:

```
python3 scripts/gen_static_findings_contract.py       # -> schemas/ + lambdas/static_scan/
python3 scripts/gen_static_scan_summary_contract.py   # -> schemas/ + lambdas/hub_ingest/
```

Each generator writes the canonical `schemas/` copy **and** the bundled Lambda copy
from one source so they can never drift. The **summary** is bundled into the Hub
validator Lambda (`lambdas/hub_ingest/`) because the Hub validates it on crossing.
The **findings** document is bundled into the static-scan Lambda
(`lambdas/static_scan/`) so that Lambda can validate its own output; it is **not**
bundled into the Hub — the Hub never parses it.
