The checker's `STORY_ID_RE` only matches `N.N[letter]` and `G-N`, so A/B/C IDs are structurally invisible to CHECK A and CHECK B whether they sit in the master table or a sibling table — and keeping them separate avoids implying they are part of the numeric pipeline dependency DAG. A.4, the stakeholder's exact complaint, is now present in the RUNBOOK build-order area.

The facts are preserved. The RUNBOOK and FLOOR_AND_HARVEST_PLAN diffs are additions-only (zero removed lines), no pipeline or governance status cell moved, and the Validation Debt Register is still empty. Statuses match the plan's section-4 table verbatim (A.1-A.4 done, B.1 + C.1-C.5 not started). PROJECT_PLAN never referenced A/B/C, so nothing there is contradicted (RD-015 holds).

The FLOOR_AND_HARVEST_PLAN table is demoted with a blockquote naming the RUNBOOK authoritative and telling future editors to update status there, not here. All narrative (sections 0-8, including the section-6 Story 2.0 validation runbook) is intact.

### Why A/B/C get their own table instead of joining the master table

The master build-order table is found by the checker on the presence of the `story`, `title`, `depends on`, `status` columns, and each row's ID is validated against `STORY_ID_RE = ^[0-9]+\.[0-9]+[A-Za-z]?$|^G-[0-9]+$`. A.1/B.1/C.1-style IDs never match that pattern, so they are parsed out of any table the checker reads — placing them in the master table would not have subjected them to CHECK A or CHECK B, and placing them in a sibling table hides nothing the checker would otherwise enforce. So the separate table is a presentation choice: the new intro prose states these stories are readiness-sequenced and explicitly *not* part of the numeric pipeline DAG, so mixing them into a table headed "Build order (dependency-driven)" with Phase/Completed columns would misrepresent them. The new table keeps the checker-parseable column signature (`Story | Title | Depends on | Status`) with a non-numeric `F&H` build-tier value and drops the Phase/Completed columns that do not apply.

### The emoji-count nuance in acceptance criterion 3

Counting status *cells*, the change adds exactly four `✅` (A.1-A.4) and six `⬜` (B.1, C.1-C.5). Counting raw glyphs across the file, the `✅` delta is +6 because two trimmed titles ("record + flip ✅", "Confirm Story 2.1 ✅") and the A.2/A.3 detail-index paragraphs ("flipped ✅", "already ✅ on `main`") reuse the check-mark inline as ordinary prose. These are not status markers and do not sit in a Status column, so no story's tracked status is affected, but a validator that greps raw glyph counts will see more than the criterion's "+4/+6" wording implies.

### Test-only CHECK B repair does not weaken the rule

The pre-existing failure: on `main` the register is empty (2.0's debt was cleared), and `check_b_advancement_gate` returns early when `registered` is empty ("register empty -> the advancement gate is not armed"). With the gate disarmed, `test_new_feature_started_while_debt_open_fires_check_b` could no longer make CHECK B fire, so it failed.

```
_seed_open_debt(runbook)      # replace "| _(empty)_ | — | — | — |" with an open 2.0 row
_git_commit_baseline(root)    # HEAD baseline: 2.2 ⬜, register non-empty
_set_2_2_status(runbook, DONE)# 2.2 ⬜ -> ✅ in working tree (new work)
```

The fix operates entirely on the fixture copy: it seeds a plausible open-debt 2.0 row so the register is non-empty and the gate is armed, commits that as the HEAD baseline (2.2 still `⬜`), then flips 2.2 to `✅` in the working tree. 2.0 is chosen deliberately because it is already in the register, so CHECK B's "reworking an open entry is allowed" clause keeps it from tripping the gate itself; only 2.2 — new, not in the register, not in the baseline started set — fires CHECK B. `check_docs.py` is untouched, so neither CHECK A nor CHECK B is loosened; the test now exercises the real gate instead of a disarmed no-op. `test_clean_tree_passes` and `test_unregistered_in_progress_fires_check_a` still pass.

Verified from the repo root: `check_docs.py` prints `PASS` (exit 0); `python -m unittest scripts.test_check_docs` reports 3 tests OK; `ruff check scripts/` is clean.

### Not tested

No unit test asserts that A/B/C rows are ignored by the checker — the load-bearing assumption behind adding them to a checker-parsed table, currently resting on the `STORY_ID_RE` non-match rather than a regression test. A one-line test that a row with ID `A.4` does not appear in `parse_story_statuses` output would lock the behavior against a future regex change. Not blocking for a docs consolidation.
